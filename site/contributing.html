Repository Roadmap Security

Contributing

Start from the roadmap, not from an idea.

Gauge is a read-only audit tool, so the bar for a change is that it cannot produce a false pass. Every change starts from a task in ROADMAP.md, arrives as one pull request with a failing test first, and updates ROADMAP.md in the same change.

Read before you write

  1. The roadmapROADMAP.md section 4 for the current focus, then the task you are taking. It is the work queue and the source of truth when an issue and its row disagree.
  2. The hard rulesARCHITECTURE_ESSENTIALS.md in full. Section 2 is not negotiable and section 12 of AGENTS.md lists the paths that need extra care.
  3. The file mapproject_structure.md: where a file goes, which way imports point and what is protected.
  4. The detail you needARCHITECTURE.md only for the section an essentials item cites, and PRD.md when scope is unclear.

Pick a task and check its dependencies

Dependencies are written on the task line as Deps:, and a task whose dependency is open is not ready. Say so on the issue rather than working around it: a green pull request for a task whose prerequisite is missing describes an order that did not happen.

If no task covers the work, add one first with the next free ID in its phase and say why. Task IDs are stable: never renumber and never reuse. The issue backlog is generated from the roadmap, so an added task needs its row in scripts/generate_issues.sh in the same pull request; --check fails when an open task has none.

The workflow

  1. Branch from mainOne task or one tightly related group per branch. Never commit to main; it is protected by a ruleset that requires a pull request and passing checks.
  2. Write the failing test firstRun it and watch it fail for the right reason. A test that fails for the wrong reason proves nothing.
  3. Implement the smallest changeNo unrequested features, no drive-by refactors, no dependency updates bundled in.
  4. Run the checks locallyThe full list is below. Paste the real output in the pull request.
  5. Update the docs the change touchesproject_structure.md when a file is added, moved or removed; PRD.md and the architecture documents when behavior changes.
  6. Update the roadmapTask boxes, a changelog row with the UTC date, the progress table and Last updated.
  7. Open one pull requestUse the template. List the task IDs, the commands you ran and their results, the docs you changed, and confirm the roadmap update.
  8. Wait for reviewDo not merge your own pull request and do not auto-merge. Never force-push a shared branch.

Branches and commits

Branch names follow the change's type and its task ID, in the form the repository already uses: feat/3.7-facts-report for a feature, docs/4.2-4.3-usage-and-readme for documentation, and a ci/ or chore/ prefix where that is the honest label. Commits are Conventional Commits with a subject under 72 characters: feat:, fix:, docs:, test:, ci:, chore:.

Write the subject about why the change exists, not only what moved. Do not put an em dash in a subject, a document or a comment.

If a command in this list does not exist in your checkout, say so in the pull request instead of silently skipping it. Never weaken, skip or delete a check to get a green run. If a test is wrong, fix it and explain why.

The roadmap rule

Every contribution updates ROADMAP.md in the same pull request, including documentation, CI and dependency changes. There are no exemptions, including Dependabot's grouped weekly updates. Four edits, every time:

  • Tick a box only when the task's "Done when" is true. Untick or add tasks when the work moves.
  • Add a changelog row at the top of section 9: the UTC date from date -u, one line on what changed, and the task IDs.
  • Regenerate the progress table with scripts/roadmap_progress.sh. Do not edit the numbers by hand; --check compares them with the checkboxes.
  • Update the Last updated line at the top of the file.

A completed task also gets its dated record on the task line and, where the file's own style keeps one, a paragraph in section 4. That record is where a claim gets its evidence: the command that was run, the ledger it read or the file it was read from.

Stop and ask the owner

AGENTS.md section 10 lists the cases. In short, ask before you:

  • Add a Go module or any dependency. The only permitted third-party module is github.com/BurntSushi/toml.
  • Add a network call or a package that dials a socket. Only internal/source and internal/sep1 do today.
  • Change a validator refusal, which makes a previously rejected input acceptable.
  • Loosen, skip or delete a check, or make one optional.
  • Change a file under a protected path: internal/source/, internal/sep1/, internal/policy/, internal/strkey/, internal/sanitize/, internal/threshold/, go.mod, go.sum, .github/ and scripts/.
  • Move or bump a pinned GitHub Action without reading the SHA to SHA diff, or pin a new one without resolving the exact upstream commit.
  • Build on a statement marked [Unverified], or resolve two documents that disagree by picking one.

A gate may gain a check, never lose one. That is the rule for .github/workflows/ and scripts/, and it is why those paths need owner review even for a one-line change.

Fixtures and goldens

  • Captured account JSON is preferred, because account data is public. Record the network, date and ledger in the sidecar testdata/horizon/README.md.
  • Where no capture can exist, a fixture is built here and labelled as built. It proves the decoder and the rules, not that the chain served the shape.
  • Testnet fixtures are perishable because testnet resets. They stay static files and tests never refetch them.
  • Hostile strings (ANSI escapes, bidi overrides, markdown) are built from fragments or written as JSON \u escapes, so no control byte sits in the file while the decoded value still carries one.
  • Golden files are regenerated only with -update and reviewed like code. The commands are on the developer guide.
  • Never commit a secret seed, even a testnet one. A test that needs a seed-shaped string builds it from fragments at runtime.

Evidence and wording

A factual claim names the run that produced it or says plainly that it is local. Documentation uses testnet observations only (decision D-16), so a mainnet figure is quoted from documentation and labelled as not observed. A claim marked [Unverified] stays unverified until the Phase 0 task that verifies it is done.

Output describes posture. It never calls an account secure or safe, and a clean report is not an approval. Reports carry the limits footer, and the README disclaimer is the same constant rather than a second sentence that can drift.

The boundary

A review is not an audit, and a passing suite is not a guarantee. Gauge ships unaudited and says so. Gauge documentation

Contributions are judged on whether they can produce a false pass, not on how large they are. A small change with a failing test that now passes and a roadmap row that names it is worth more than a large one without either.
