Developers

The code is the specification.

Gauge is one Go module, the standard library and one TOML parser. There is no framework, no plugin loader and no rule language. This page is the map: which package does what, which way imports point, the tests that pin behavior, and what a change has to prove before it merges.

Build and run from source

Go 1.27.3, which is what go.mod declares. No wallet, no credentials and no Stellar SDK.

Shell
git clone https://github.com/posture-sec/guage
cd guage
go build -o stellar-gauge ./cmd/stellar-gauge
./stellar-gauge version

The binary has three subcommands, check, audit and version, plus help. Their flags and exit codes are on Guides.

Imports point one way

This direction is a hard rule, not a convention. A reversal is a design change and needs the owner.

Dependency direction
model <- strkey, threshold, sanitize
      <- policy, source, sep1
      <- rules
      <- report
      <- run
      <- cmd/stellar-gauge
  • rules reads a sep1.Result value; it never fetches one. Its direct imports are model, policy, sep1, threshold, fmt, sort and strings. Check that on imports (go list -f '{{.Imports}}' ./internal/rules), not on -deps, which shows net/http transitively because sep1's result types and its client share a package.
  • Only source and sep1 perform network I/O. Only cmd, run and report write to stdout, stderr or a file, and the shipped commands write nothing but stdout and stderr.
  • No os/exec, no unsafe, no init() side effects and no package-level mutable state.
  • The only third-party import is github.com/BurntSushi/toml, and only inside policy and sep1.

Adding a rule

  1. Write the functionA pure function in internal/rules/<family>.go that reads only its Context and returns findings. It must not sum weights, apply the 20-signature cap or filter zero-weight signers itself; those come from internal/threshold.
  2. Register itOne entry in the registry in internal/rules/rules.go, with the rule ID and the function. rules.All returns them in evaluation order.
  3. Prove both sidesA positive and a negative fixture, or the same fixture under two declarations where the rule is a comparison. The test should fail for the right reason before the rule exists.
  4. Regenerate the goldensOnly with -update, then read the diff as code.
  5. Weight it if the catalog doesA rule the catalog phrases "by role" gets its cells in internal/policy/roles.go and in PRD.md Appendix A. A role raises a severity and never lowers one.
  6. Tell the readerPRD.md 6.1, ARCHITECTURE_ESSENTIALS.md 8, and the article on the rule catalog. A rule that ships without its article makes the site stale.

The two golden commands, run from the repository root:

Shell
go test ./internal/run -run TestAppendixBScenarios -update
go test ./internal/report -run 'TestTextGolden|TestJSONGolden' -update

The first rewrites the Appendix B pairs under testdata/golden/; the second rewrites the two sample.* goldens. A new scenario needs the first run once, and the diff is where a wording or severity change becomes visible.

Adding a policy field

  • internal/policy/config.go for the declaration, then the expectation or accept logic beside it. Omitted expectations stay pointers, because "not declared" is not zero or false.
  • Strict-decode tests: an unknown key is an error, a duplicate is an error, and the raw file is scanned for a seed-shaped token including in comments.
  • gauge.example.toml, which a test loads through the real parser so the example cannot rot.
  • ARCHITECTURE.md 7 for the model, and a version bump if the change is breaking. The loader accepts version 1 only.

Tests that pin behavior

LayerHow it is tested
Rules and threshold mathTable tests, plus a randomized subset search for reachability and the minimum signer count. The math is not restated in a rule.
Source failuresA fake Horizon over net/http/httptest for 200, 404, 429, 5xx, slow, oversize, malformed, a wrong passphrase and redirects.
Identity guardFourteen blocked address classes, a DNS answer that changes between resolutions, and a redirect target that resolves private. The assertions are on the address the dial received.
ReportsGolden text and JSON files, sanitization of hostile strings and determinism.
Scenariosinternal/run/scenarios_test.go runs the Appendix B numbers as cases over the production source client, in both formats.
CLIIn-process runs for flags, usage errors, exit codes, the gate G3 failure modes and the zero-config fact block.

Fuzz targets exist for the two parser-adjacent packages. They are local smoke runs, not CI jobs, and each command names one package because -fuzz refuses more than one:

Shell
go test ./internal/strkey -run '^$' -fuzz=FuzzClassify -fuzztime=10s
go test ./internal/sanitize -run '^$' -fuzz=FuzzText -fuzztime=10s
go test ./internal/sanitize -run '^$' -fuzz=FuzzFenced -fuzztime=10s

Fixtures under testdata/horizon/ carry their provenance in the sidecar README.md: captured from testnet, or built here and labelled as built. A built fixture proves the decoder and the rules, not that the chain ever served the shape.

Limits that are not changed casually

These numbers are the reason a hostile or slow endpoint cannot turn into a hung job or an unbounded read. They live in protected packages and change only with owner review.

ClientBound
Horizon10 second timeout, 1 MiB body cap, 3 retries with capped backoff, at most 8 concurrent requests, redirects refused.
stellar.toml10 second timeout, 100 KiB cap, 3 hops, 2 retries, and the dial-time address guard. The path is fixed at /.well-known/stellar.toml; Gauge never fetches a path a chain value supplied.
Policy file1 MiB, strict decode, rejected before any request when it does not parse.

No response body is logged. A report quotes an identity document only through the fields SEP-1 defines that the parser recognized, sanitized like every other chain-derived string, plus the fetch facts: status, hops, bytes and whether CORS was present.

Where the design lives

  • ARCHITECTURE.md: the design, the data models, the protocol citations and the red-team review. Section 6.3 holds the threshold semantics; section 6.5 the identity fetch; section 11 the CI surface.
  • ARCHITECTURE_ESSENTIALS.md: the hard rules, short enough to read before every change.
  • PRD.md: scope, requirements and Appendix A, the role table the severity floors come from.
  • project_structure.md: the annotated tree, protected paths and naming.
  • ROADMAP.md: what is left, what is blocked and why.

If a document contradicts the code, the code is the source of truth for behavior and the document is fixed in the same pull request that found it. If two documents disagree about a rule, that is a question for the owner rather than a choice to make quietly.

The boundary

A green test suite proves the code does what the tests say. It does not prove the rules are right about your account. Gauge documentation

No third party has reviewed this code. The sixteen rules are tested against fixtures and captured shapes, and no operator outside this repository has reviewed a finding from it yet, which is task 4.1 and gate G4.
