Fail-closed behavior

A run either produces a report it trusts or refuses to produce one. These cases are exercised by the CLI tests, including gate G3.

ConditionExitReport
Endpoint unreachable3No report. The source failed.
Oversized response3No report. The body cap was hit.
Malformed JSON3No report. Strict decode failed.
Wrong network passphrase1Report with acct-network-mismatch. No account was read.
Account absent (404)1Report with acct-missing for that account.
Unknown policy key2No report. The policy is rejected before any request.
Secret seed in the policy or arguments2No report, and the seed is never echoed.
Missing policy file2No report.
Rule panic3Report with src-rule-panic; the account's result is incomplete.

A non-zero exit is the expected behavior for the first three rows. Treating exit 3 as a flaky pass is the failure mode this design tries to prevent.

Security and project hygiene

  • OpenSSF Scorecard runs on every push to main and weekly; the README badge reports its current score.
  • Dependabot watches the Go module and the pinned GitHub Actions.
  • govulncheck, staticcheck and go vet run in CI.
  • No secret is accepted, stored or echoed. A seed found anywhere in a policy is a hard failure.
  • The repository has a security policy and a private reporting route. Read SECURITY.md before reporting.

Passing checks are not an audit. No third party has reviewed this code, and the project says so in every banner and release note.

The boundary

Gauge reads public ledger state only. It cannot see who holds a key, whether signers are separate people, or off-chain controls. Report limits footer

A clean report is a posture result, not proof that the account cannot be compromised. A failing report is evidence of a disagreement, not necessarily an incident. Read both with the policy file open beside them.
