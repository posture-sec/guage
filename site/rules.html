Rule catalog

Sixteen checks. Seven shipped.

Every rule has a stable kebab-case ID, a written condition and a severity. A finding names the rule, the account, an evidence line and a fingerprint that identifies it. An accepted risk matches on rule and account, not on the fingerprint. All sixteen are written out on this page: the seven that run today, and the nine that do not, each with the condition a contributor has to satisfy and the task that blocks it.

7 live 9 specified Baseline severities until 3.4

The seven live rules

These are registered in internal/rules, covered by positive and negative fixture cases, and exercised end to end by the CLI tests.

acct-missing

HIGH Live

A requested account returned 404. The endpoint answered, so this is a statement about the account, not about the network. The account may never have been created, or it may have been merged into another account. The run continues and reports the other accounts.

Evidence
endpoint URL returned not found
Acceptable
No. An acceptance cannot hide a missing account.
Exit effect
HIGH fails the default --fail-on high and produces exit 1.

acct-network-mismatch

HIGH Live

The endpoint's network passphrase differs from the network the run requested. No account is fetched from that endpoint at all, because an account ID can exist on more than one network and the report would describe the wrong chain. Each requested account is listed as skipped with this finding.

Evidence
expected Test SDF Network ; September 2015, endpoint reports Public Global Stellar Network ; September 2015
Acceptable
No.
Exit effect
HIGH fails the default threshold and produces exit 1. The run did not read an account, but it did complete and name the disagreement.

flag-drift

WARN Live

A flag the policy declares disagrees with the chain. Only declared flags are compared, so an omitted flag can never drift. The comparison runs in a fixed order: auth_required, auth_revocable, auth_immutable, clawback. The evidence lists each disagreement.

Example
auth_required declared false, observed true
Acceptable
Yes, with a reason and an optional expiry. The owner adds accept entries.
Exit effect
WARN is below the default --fail-on high. It produces exit 1 only under --fail-on warn.

flag-undeclared-clawback

WARN Live

Clawback is enabled and the policy says nothing about clawback. A declared value, true or false, suppresses this rule: declared true is a declaration, and declared false that disagrees with the chain is flag-drift instead.

Evidence
clawback observed true, and no clawback expectation is declared
Acceptable
Yes, with a reason and an optional expiry.
Exit effect
WARN. Exit 1 only under --fail-on warn.

id-no-home-domain

WARN Live

The policy declares a home_domain and the account publishes none on chain. The trigger is the declaration, not the role: the role table that would decide which accounts are expected to publish one is task 3.4, and rules may not hardcode a role set. A check run declares nothing, so it cannot raise this rule.

Evidence
home_domain declared "example.org", observed none
Acceptable
Yes, with a reason and an optional expiry.
Exit effect
WARN. Exit 1 only under --fail-on warn.

id-toml-unreachable

WARN Live

The account publishes a home domain and its stellar.toml could not be fetched or parsed under the guard. It fires the same way when a domain was observed and never fetched at all: an identity Gauge could not verify is a warning, never a pass. The evidence names the step that failed, so a domain that resolves to a blocked address is distinguishable from one that serves an oversized or unreadable document. Nothing from the document is quoted; the detail phrase is one this repository wrote. A fetcher that cannot be built at all is a run that did not complete: exit 3, no report.

Evidence
step guard; detail the host name resolves to a private address, which Gauge will not dial; status 0
Acceptable
Yes, with a reason and an optional expiry.
Exit effect
WARN. Exit 1 only under --fail-on warn.

id-toml-account-unlisted

WARN Live

A readable stellar.toml does not name this account in ACCOUNTS. The rule only speaks about a document it could read, so an unreachable domain raises one finding rather than two. Entries that are not account addresses are counted and never echoed, which keeps a malformed or hostile list out of the report. The document's NETWORK_PASSPHRASE is carried in the result but compared by no rule today.

Evidence
home domain example.org lists 2 accounts; this account is not among them
Acceptable
Yes, with a reason and an optional expiry.
Exit effect
WARN. Exit 1 only under --fail-on warn.

The nine specified rules

Each of these has a stable ID, a written condition and a severity. None is registered in internal/rules, so a run today evaluates none of them and no exit code depends on one. What follows is the contract tasks 3.1 and 3.4 have to satisfy, written from PRD.md 6.1, PRD.md Appendix A and ARCHITECTURE.md 9 rather than from an implementation, which is why the evidence rows say what a finding must name instead of quoting a line no program has printed.

Nine of them lean on one piece of arithmetic that does not exist yet. internal/threshold will hold Reachable and MinSigners, and its rules are settled: weights are summed and must reach or exceed the threshold, thresholds and weights run over the ranges Stellar defines, a signer participates only above weight zero, ed25519 and hash(x) signers count toward standing control while a pre-authorized transaction signer authorizes one named transaction and does not, and MinSigners takes weights largest first and accumulates. Two edge cases, a threshold of zero with no weighted signer and signatures left over after the threshold is met, remain unverified because settling them needs a testnet transaction and this project forbids itself from building one. That is the reason these nine are not shipped, and no amount of review changes it.

sig-no-signing-weight

HIGH Specified

No signer on the account carries weight above zero, so no signer participates in any tier and the account can never sign anything again. It cannot move its own balances, cannot rotate its own keys and cannot lower its own thresholds, because each of those operations needs a signature from the account it changes. Undeclared, that shape is an accident or the end of a compromise. Declared, it is a decision, and the catalog says so: an issuer that declares expect_locked = true is describing an account whose job was to issue and then step aside, and for that account the finding is INFO.

Evidence
The account address, how many signers the read returned, and the fact that every one of them sits at weight zero. Horizon reports the master key inside the signer list, so a master key at zero with no other entry is what this rule sees as an empty account.
Acceptable
Yes, with a reason and an optional expiry. expect_locked is the declared form of the same fact, so a locked issuer that also accepts this finding has declared it twice.
Exit effect
HIGH would fail the default --fail-on high. INFO fails no threshold at all, which is the point of the exception.
Blocked by
Task 3.1, which registers the signer family, and task 3.4 for the expect_locked downgrade, because no rule may read a role today.

sig-threshold-unreachable

HIGH Specified

For each of the three tiers, whether the signers that exist can add up to what that tier demands. When they cannot, the tier is dead: no combination of keys anyone holds will ever authorize an operation in it again, and nothing can be gathered after the fact because the weights that would have made the total are not on the account. The high tier is the one that ends an account, since changing signers and changing thresholds both run at high. An unreachable high tier freezes the account in exactly the shape that made it unreachable.

An account with no participating signer makes every tier above zero unreachable, so this rule and sig-no-signing-weight fire on the same read and say different things about it: one names the missing weight, the other names the tier that is now permanently dead.

Evidence
The tier that cannot be reached, the threshold it demands, and the total participating weight available to it.
Acceptable
No. This is the only rule in the signer family that cannot be accepted at all; it sits on the non-acceptable list in ARCHITECTURE.md 6.6 beside the two account rules. An acceptance records a risk an operator has decided to live with, and an unreachable tier is not a risk but a statement that a class of operation can never happen.
Exit effect
HIGH, so it would fail the default --fail-on high, and no acceptance would hide it.
Blocked by
Task 3.1, which is also where Reachable gets written, and task 0.7 behind it.

sig-threshold-order

WARN Specified

low <= medium <= high. Horizon accepts any three numbers in any order, so an account can carry a medium tier stricter than its high tier and remain perfectly legal. It stops being readable: the three tiers are how an owner says which operations need how much agreement, and when they run backwards nothing on the account shows which number anyone meant. Stellar documents the order as a recommendation rather than a requirement, which is why this is a warning and not a HIGH. An out-of-order account may be exactly what its owner wanted and has merely failed to explain itself.

Evidence
The three tiers as the chain reports them, and the pair that violates the order.
Acceptable
Yes, with a reason and an optional expiry.
Exit effect
WARN, so exit 1 only under --fail-on warn.
Blocked by
Task 3.1. The thresholds themselves are already parsed into the snapshot, so this is the one rule in the family whose input exists today.

sig-single-key-high

By role Specified

MinSigners(signers, high) == 1: one key alone reaches the high threshold, so a single stolen credential authorizes everything the account can do, including replacing every other signer. The rule reads weights rather than counting entries, which is what makes it worth having at all. A five-signer account in which one entry holds weight 9 and four hold weight 1 is a single-key account that looks conservative in any list of signers. Only participating signers count, so a key at weight zero reaches nothing, and a pre-authorized transaction signer does not count toward standing control either.

Severity is the role table: HIGH for issuer and treasury, WARN for merchant and distribution, INFO for other. PRD.md Appendix A writes those rows and task 3.4 turns them into behavior. There is no baseline number for this rule until then, and this page is not going to invent one.

Evidence
The signer that reaches the tier on its own, its weight, and the tier it reaches.
Acceptable
Yes, with a reason. An operator who has decided that one custodial key is enough for a receiving account can accept the finding instead of re-weighting the account, and the acceptance is what makes that decision visible rather than burying it.
Exit effect
Decided by 3.4. On the rows as written it is HIGH for an issuer or a treasury, which would fail the default threshold, WARN below that, and INFO for other, which fails nothing.
Blocked by
Task 3.1 for the arithmetic and task 3.4 for the role rows, with task 0.7 behind both.

sig-hashx

WARN or HIGH Specified

A hash(x) signer is a signer whose key is the hash of a value instead of an ed25519 public key. To use it its holder reveals the preimage, the ledger hashes what it was given and matches it against the stored key. That is how pre-signed and time-locked arrangements are built, and it is also a signer that anyone who finds the preimage can operate, with no key to guard and nothing to notice being taken. The rule is WARN for one being present and HIGH when that signer's weight alone reaches the medium tier, because at that point a preimage nobody has published yet is a medium-tier key.

Gauge decodes and labels this type today: internal/source maps Horizon's sha256_hash onto the internal hash_x. No captured account carries one, in testdata/horizon/ or in posture-sec/stellar-account-fixtures, because every signer key in either set is a G... address. The fixture behind this rule is therefore hand-built and labelled as such until task 3.6 decides what the Appendix B set actually needs.

Evidence
The signer's key, its weight, and the tier that weight reaches on its own.
Acceptable
Yes, with a reason and an optional expiry.
Exit effect
WARN at presence, HIGH at medium-tier reach, so only the second fails the default --fail-on high.
Blocked by
Task 3.1 for the severity split, and a real capture of the shape, which is 3.6's question rather than this rule's.

sig-unexpected-signer

By role Specified

A signer on the account that the declared expected_signers list does not name. The declaration is the whole rule. expected_signers is a pointer in the policy, so an absent key makes no claim and the rule stays silent, while expected_signers = [] is a positive claim that this account should carry no signer at all. A key its owner added and had not yet written into the file is exactly what this finding is for, and a key nobody added is the same finding with a worse explanation attached to it.

Appendix A raises presence to HIGH for an issuer, where a new signer is the ordinary shape of a compromise, and writes signer and threshold drift as HIGH for a treasury and WARN for merchant and distribution. Whether a treasury's "signer drift" row covers presence as well as weight is a decision task 3.4 makes; it is not a mapping this page gets to guess on its behalf.

Evidence
The signer's address, its weight, and the fact that no declared entry names it.
Acceptable
Yes, with a reason and an optional expiry, and the expiry matters here more than anywhere else in the catalog: accepting a signer that appeared is a statement that it will be explained or removed by a date.
Exit effect
Decided by 3.4. HIGH on an issuer as the table reads, below the default threshold on the roles that come out WARN or INFO.
Blocked by
Task 3.1 for the comparison and task 3.4 for the role rows.

sig-missing-expected

HIGH Specified

A signer the policy declares is not on the account. Someone removed a key: the rotation of a retired device that was never written back into the file, or the removal of the one signer that was not meant to go. HIGH rather than a warning because an absent signer cannot be restored by its own owner alone: putting a key back is a high-tier operation, so recovery belongs to whoever still holds enough weight, which is the same class of event as an unreachable threshold and a good deal easier to fix. It is also the rule that says whether a policy still describes anything.

With sig-unexpected-signer it forms the two halves of one claim. Both silent is what "the signers are exactly the ones you declared" means. Silence from only one of them is not.

Evidence
The declared address and the fact that no signer entry on the account carries it.
Acceptable
Yes, with a reason and an optional expiry.
Exit effect
HIGH, so it would fail the default --fail-on high.
Blocked by
Task 3.1. Its severity does not depend on role, which makes it the least blocked of the nine.

sig-weight-drift

By role Specified

A declared signer is present and its weight is not what the policy says. The set of keys matches, so a check that looks only at presence stays quiet, and the account's distribution of power has changed underneath it anyway. Raising one signer from 1 to 6 can turn a five-key account into one a single key reaches at medium; lowering one from 6 to 1 can make a tier unreachable while every name on the account is exactly where it was left. Weight is what the threshold math reads, so this is the rule that keeps that math honest about intent.

Evidence
The signer's address, the declared weight and the observed weight.
Acceptable
Yes, with a reason and an optional expiry.
Exit effect
Decided by 3.4. Appendix A gives a treasury HIGH for signer drift, merchant and distribution WARN and other INFO, and does not name weight drift for an issuer at all, so that cell is one of the rows 3.4 has to write rather than read.
Blocked by
Task 3.1 and task 3.4.

thr-drift

By role Specified

Any declared tier differs from the chain, in either direction. Thresholds decide how much agreement an operation needs, so a change here rewrites the meaning of every weight on the account without touching a single signer. Lowering high from 9 to 3 on an account whose three signers hold 3 each leaves an account that any one of them can move alone while its signer list still looks careful. Raising a tier can push it past the total available weight, and that case belongs to sig-threshold-unreachable rather than here, which is why both rules exist and why one edit can produce two findings.

Evidence
The tier, the declared number and the observed number.
Acceptable
Yes, with a reason and an optional expiry.
Exit effect
Decided by 3.4. Appendix A names threshold drift HIGH for a treasury and WARN for merchant and distribution, and, as with weight drift, says nothing about an issuer.
Blocked by
Task 3.1 for the comparison and task 3.4 for the role rows.

What is not shipped

The nine specified rules are a contract for the next phases, not behavior you can rely on today. They are written out above anyway, each with the condition a contributor has to satisfy, the severity question it raises and the task that blocks it, so that the contract can be worked from without reading Go source. The signer and threshold rules wait on threshold semantics that task 0.7 could not verify without submitting a transaction, which Gauge forbids itself to do. Role-based severities are task 3.4.

Read the status before trusting a pass. A run evaluates the seven live rules. A clean result means those seven agreed with your policy; it says nothing about signers, thresholds or any rule marked Specified.
