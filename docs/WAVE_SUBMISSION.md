## 4. Maintainer runbook for the cycle

Quoted panel names are from the Drips maintainer docs.

1. Sign in to the wave portal with the GitHub account that can administer the `posture-sec` organization. A phone number may need verifying before participating in a wave.
2. Install the Drips Wave GitHub App on the organization hosting your repositories. Organization scope matters: installing it on one repository only will not sync the others.
3. Under Maintainers, Orgs and Repos, sync and apply the repository to the Stellar Wave program. Applications require approval from the wave organizers.
4. If rejected, do not re-apply through the same route: appeal from the Orgs and Repos panel after the work has visibly improved.
5. Under Maintainers, Issues, add each issue with Add to Wave and set its tier there. The three tiers are Trivial, Medium and High. Do not use the GitHub `Stellar Wave` label as the shortcut: issues added that way are automatically Trivial at 100 points regardless of the real work, which would misprice 28 Medium and 3 High tasks in this backlog.
6. During the active week, check the dashboard daily to review applications and assign contributors.
7. Merge pull requests promptly and mark issues Resolved before the wave ends, or contributors lose their points. Unfinished work carries into the next cycle.

**Project description.** Gauge is a command line tool that reads the public configuration of your own Stellar accounts and compares it with what you said you expect. On Stellar, control of an account is a set of weights and thresholds stored on-chain: who can sign, how many signatures a high-value operation needs, which flags the issuer turned on. Those settings are public, rarely reviewed, and the reason accounts get locked or quietly gain a signer. Gauge fetches an account through Horizon, checks it against a small declared policy file, and exits nonzero when reality and intent disagree, so a scheduled run in CI catches a change to a treasury or issuer account the day it happens. It is read-only, never accepts a secret key, and treats every value it downloads as hostile input. The scale argument: Stellar averaged about 4.9 million daily transactions and roughly 63,000 daily active addresses in Q2 2026, with tokenized real-world assets on the network past $3 billion, and the accounts holding much of that are configured by people with no security review process.

**Repository description.** One Go module, `github.com/posture-sec/guage`, binary `stellar-gauge`. No smart contracts and no frontend, so there is no deployment to verify and no app URL: the deliverable is a static binary and a report. Dependencies are the standard library plus one reviewed TOML parser. Layered packages with a declared import direction, rules as pure functions, and a roadmap file that CI enforces on every pull request.

**Planned issues.** 43 open issues as of 2026-11-03, read from `search/issues?q=repo:posture-sec/guage+type:issue+state:open`, generated from `ROADMAP.md` by `scripts/generate_issues.sh`, so each one is a roadmap task or a readiness gate with its acceptance criteria taken from the task's own "Done when" line. Seventy-three were created on 2026-10-30 and thirty have since been closed by the pull requests that ticked their tasks; `scripts/generate_issues.sh --check` runs in CI as part of `roadmap-check / gate` and fails a pull request whose backlog rows no longer cover every open task. Tiers as labelled: 11 `complexity: trivial`, 21 `complexity: medium`, 2 `complexity: high`, and nine gate issues with no tier label because they are readiness checks rather than wave work. By area: docs 13, ci 12, rules 9, source 2, sep1 2, threshold 2, run 1, report 1, policy 1, and every open issue carries exactly one. No open issue is labelled `good first issue` or `help wanted`, and none carries the `Stellar Wave` label, so this draft no longer claims otherwise: the five dependency-free research tasks it used to point at (0.5, 0.8, 0.9, 0.12, 0.13) are closed, and the seven open `type: research` issues each need something a contributor cannot supply on day one, an owner decision (6.4, D-07), a relationship with a real operator (0.4, 4.1) or a testnet transaction Gauge is written never to build or submit (0.7). ## 7. The organization has three repositories now

`posture-sec/airlock` went public on 2026-11-02. It is the sibling scanner: a Python 3.11 CLI that audits Stellar and Soroban *repositories* for supply-chain compromise and release-integrity gaps, where Gauge audits *account configuration* on-chain. Same owner, same conventions, no shared code, and it arrived by recovery rather than by plan: the account that owned it (`airlock-sec`) was suspended, so the repository, its history and its documentation were moved here and re-pointed, which is task 1.15 in its own roadmap.

`posture-sec/stellar-account-fixtures` went public the same day, and it is not a CLI. It is a corpus: nine account reads captured from Horizon, eight on mainnet and one on testnet, re-serialised with sorted keys, each beside a sidecar carrying the source URL, the UTC capture time, `last_modified_ledger`, the Horizon version that served it and the SHA-256 of the bytes next to it, plus a `validate.py` that recomputes all of that and fails a shape label the bytes do not show. It exists because of a method problem this repository hit at 0.6: a rule written against a hand-typed fixture passes until the first real account disagrees with the invention. What changes here is not Gauge's readiness but the shape of the decision:

1. One Drips Wave App installation at org scope covers all three repositories, so the install and phone-verification steps happen once.
2. The per-org cap and the per-org budget ceiling are shared, now between three applicants rather than two. Nothing in the maintainer docs says how large either is, so the cost of applying more than one in a cycle is unknown, and a rejection is not refundable: the docs say a rejected repository cannot be re-applied and appeals are capped at three with waiting periods between them.
3. The ranking of readiness is not the ranking of fit, and the percentages now point in a direction that needs explaining. Read from each repository's own generated table, the corpus has the highest completion of the three siblings: 17 of 24 at 71%, against Airlock's 45 of 95 at 47%. That compares 24 tasks of corpus maintenance with 95 tasks of scanner work, and on the things a wave cycle actually uses the corpus is still the thinnest of the three: no docs site, no tag, 2 of its own 5 gates, and no wave-scoped issue at all, while Airlock has fifteen drafted under `docs/wave/` and clears 0 of 10 of its gates. Airlock remains the most complete submission on the counts that table shows. Gauge has the better story to demonstrate (a live read of a real account, a docs site, a Scorecard badge) and is thinner on rules until the signer family lands. What the corpus has, and what the 71% actually measures, is work shaped for strangers: its remaining Phase 2 tasks are finding accounts that carry one of the six shapes its README prints as missing and running `tools/capture.py` on them, which is a search plus one command against a validator that refuses a dishonest sidecar, and three of them closed exactly that way on 2026-11-03 with no code change.
4. That ordering is still not a reason to submit any of them first. Airlock's runbook puts the Drips application *before* publishing the issues, because on an unapproved repository the `Stellar Wave` label is stripped silently and the issues score nothing; the same would apply to the corpus, whose issues would need wave-scoping and tiers before a cycle, not after. Each repository's own gate list decides, not this file.

The practical consequence for this packet: read the caps on the dashboard first, and if the cap allows one repository per cycle, spend that one on whichever has its gate list clear on the day the window opens. With three applicants and one maintainer, more than one wave per cycle is still not realistic, because a maintainer has to review contributor pull requests during the active week and one person running two waves at once is how issues end up unresolved at the deadline, which costs the contributor their points rather than costing the organization anything.
